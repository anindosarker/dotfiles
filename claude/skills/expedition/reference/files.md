# Release files

## Layout

```
.ai/plans/v0.<n>.x/<owner>/
├── <release>-plan.md       ← authored: ## Goals, ## Deliverables
├── decisions.md            ← accepted decisions, D<n> items under round headings, each with its epic tag line
├── findings.md             ← problems found in the code, F<n> items under round headings
├── process.md              ← this project's facts for the release, about ten P<n> rules, two to five explicit bullets each (branches, milestone branch and worktree, merge, release, checks on the shared machine, agent sandbox, public surface, commits, shared files, plans); copied from the previous release by new_cycle.py, audited and rewritten rule by rule with the owner before the run (SKILL.md Process notes)
├── plan/specs/NN-<slug>.md ← authored: one spec; follow-up specs NN.M-<slug>.md; section 2.1 holds one ### Milestone: <name> block per milestone
├── plan/epics/E<n>.md     ← one per epic, from new_epic_file.py: Decisions and Specs lines, Notes the specs cannot hold, acked by the runner
├── run/trackers/NN-<slug>-tracker.md ← one per milestone: status, task lines, check lines, staged attention items; fix-<slug>-tracker.md for a fix milestone
├── run/attentions/ATTENTION-<YYYY-MM-DD>.md ← A<n> items for the owner, written during the run
├── run/handoffs/          ← write-handoff output
├── status/ownership.md     ← generated, like everything under status/ (never edited by hand); ownership.py: | Milestone | Spec | Depends on | Derived from | Files | and ## Critical paths, one line per epic
├── status/sprints.md       ← sprints.py, by the lead on go and the runner on merge: the grid, one row per milestone, one column per sprint; ticked by the runner
├── status/index.html       ← the swimlane page, copied from templates/swimlanes.html by new_cycle.py, refreshed by swimlanes.py when the template is newer; a render, git-ignored, never committed
├── status/data/sprints.data.js ← regenerated by swimlanes.py (and data/sprints.json): the page's data; git-ignored, never committed
└── reference/              ← optional supporting material, by hand
```

Older releases (v0.8.x and earlier, and v0.9.x until migrated) keep the flat layout. The scripts do not read them: a folder without `plan/` is refused with one line naming `migrate_layout.py`, which moves it once.

Formats of each file: [formats.md](formats.md).

## <release>-plan.md sections

Exactly two, in order: `## Goals`, `## Deliverables`. No other `## ` section. Process rules are cited `(P<n>)`, never repeated.

Deliverables table: columns `#`, `Spec` (linked to the spec file), `Scope`. Scope is one outcome sentence under 120 characters: no file lists, no mechanics; the spec file holds them.

Milestones live in the spec files, not in `<release>-plan.md`: each spec's section 2.1 holds one `### Milestone: <name>` block per milestone with the lines `- Files owned: a, b`, `- Depends on: <milestone names or spec numbers, or none>`, `- Review: none | fable`, then `- Task 1: ... Checks: ...` lines. Branch and worktree are assigned at launch and recorded in the milestone's tracker, never in the spec.

`status/ownership.md` is generated by `ownership.py` from those blocks: a table `| Milestone | Spec | Depends on | Derived from | Files |` and a `## Critical paths` section, one line per epic (`- E6: 09 Theme panel shortcut row > 10 Theme color picker`). An edge from A to B exists when B lists A under `Depends on` or when A and B share a file (lower spec number first); `Derived from` lists the shared-file edges as `<milestone> (file)`, so a reader sees why a column was assigned. A milestone's column is the longest chain ending at it plus one, across every epic. An epic's critical path is the longest chain over that epic's milestones and the edges between them, ties by lower spec number. A file shared by two milestones of the same column, or a dependency cycle, is a script error naming the file and the two milestones, fixed in the spec.

Every file the release changes has exactly one milestone owner while it runs. Two milestones that share a file sit in different columns, or the two merge. Shared files no milestone owns (`<release>-plan.md` appends, changelog blocks, generated registry and docs copies) follow the release's `process.md`. What two or more milestones need (dependency adds, lockfile, lint or CI config, shared helpers, baseline captures) lands as the first sprint's shared milestone.

Checks live in each task's `Checks:` and the release's `process.md`; Acceptance in each spec's `Acceptance:` line (programmatic or judged); the release in the release spec; sandbox rules in `process.md`.

`<release>-plan.md` is not frozen: specs add rows, each go fills their Epic cells.

## status/sprints.md

In `status/`: a title, an `Updated: <date time>` line, one table `Milestone`, `S1` .. `Sn`. Grid only: one row per `status/ownership.md` row of a spec with an Epic line, row text `E1 01 Filtering` ([formats.md](formats.md)); fix milestones added mid-run get a row from `new_fix.py`. A cell is `[x]` merged, `[ ]` running, `·` not started, `[!]` blocked (the reason stays in the milestone's tracker under `## Attention`). No legend, no prose, nothing under the table.

`sprints.py` writes it on go (the lead, the epic's rows with `·`) and on merge (the runner); the runner ticks it at every boundary. A regeneration keeps the ticks. `status.py` flags a `status/sprints.md` whose rows differ from `status/ownership.md`.

A fix milestone (no spec of its own) gets a tracker, `run/trackers/fix-<slug>-tracker.md`, whose first line cites its findings, for example `(F3, F4)`, and a grid row in the running sprint column; `new_fix.py` writes both. `status.py` counts those citations.

## Scripts

Run from inside the repo, as `python3 -I <script> <release>`. They never overwrite an authored file.

| Script | Does | When |
|---|---|---|
| `python3 -I <skill>/scripts/new_cycle.py v0.<n>.x [--owner X]` | creates the release folder with the `<release>-plan.md` stub (`## Goals`, `## Deliverables`), `decisions.md` and `findings.md` (from the templates, with a `## Round 1: discussion, <today>` heading), the subfolders `plan/specs/`, `plan/epics/`, `run/trackers/`, `run/attentions/`, `run/handoffs/`, `status/data/`, `status/index.html` from `templates/swimlanes.html`, appends `.ai/plans/*/*/status/index.html` and `.ai/plans/*/*/status/data/` to the repo's `.gitignore` when missing, and `process.md` copied from the newest earlier release (else from `templates/process.md`, placeholders to fill) | a new release |
| `python3 -I <skill>/scripts/new_spec.py v0.<n>.x NN <slug> "<Title>" "<scope>"` | creates the `plan/specs/NN-<slug>.md` stub and the first milestone's tracker `run/trackers/NN-<slug>-tracker.md` (`Status: planned`), adds the row to the `<release>-plan.md` Deliverables table in order; refuses a title, scope or template citing a superseded decision | each new spec or follow-up spec |
| `python3 -I <skill>/scripts/new_spec.py v0.<n>.x --epic E<n> <spec numbers or D ids>` | writes `- Epic: E<n>` under each spec's title line (a D id names the specs citing it), the tag line `[E<n>]` under each decision those specs cite and each named D id, and `E<n>` in each spec's Deliverables Epic cell; an existing Epic line or tag is kept; refuses a spec citing a superseded decision | on go |
| `python3 -I <skill>/scripts/new_epic_file.py v0.<n>.x E<n>` | writes the `plan/epics/E<n>.md` stub (`# E<n>`, empty `Decisions:` and `Specs:`, `## Notes`) and commits it; refuses an existing file | the moment the previous epic's RUN is sent |
| `python3 -I <skill>/scripts/ownership.py v0.<n>.x` | reads the `### Milestone:` blocks of every spec linked from `<release>-plan.md` and every `run/trackers/fix-<slug>-tracker.md` (a fix milestone: name from its title, optional `Files owned:` and `Depends on:` lines), writes `status/ownership.md` (milestone, spec, depends on, derived from, files, `## Critical paths` one line per epic; `--epic E<n> <spec numbers>` counts untagged specs as E<n>); errors on a shared file inside one column or a dependency cycle, naming the file and the two milestones. `--overlap <spec numbers or D ids>`: check mode, writes nothing, reports files shared with milestones of running sprints, exit 1 on a shared file | after each spec is written; `--overlap` before the sprint hint and on the `SPECS` message |
| `python3 -I <skill>/scripts/swimlanes.py v0.<n>.x` | reads `status/sprints.md`, `status/ownership.md` (table and `## Critical paths`) and `<release>-plan.md`, writes `status/data/sprints.data.js` and `status/data/sprints.json` (each epic's path milestones marked critical, `criticalPaths` per epic, `criticalPath` their union); copies `templates/swimlanes.html` to `status/index.html` when the template is newer or the page is missing | right after every `sprints.py` run: lead on go, runner on merge |
| `<skill>/templates/swimlanes.html` | the swimlane page: lanes per epic, sprint columns, Depends on arrows, red arrows only between two milestones of one epic's path; reads `data/sprints.data.js` beside it | copied, never edited in a release |
| `python3 -I <skill>/scripts/migrate_layout.py v0.<n>.x` | `git mv` of the flat release folder into the `plan/`, `run/` and `status/` layout above; copies the page template; appends the two `status/` render lines to `.gitignore` when missing; rewrites the plan's spec links and the old paths inside the handoffs and epic files; reruns `ownership.py`, `sprints.py`, `swimlanes.py`, `status.py`; commits nothing; refuses a folder that has `plan/specs/`, merges into a target folder made early (an epic file) | once per release still on the flat layout |
| `python3 -I <skill>/scripts/sprints.py v0.<n>.x` | writes the `status/sprints.md` grid from `status/ownership.md`: the computed sprint columns, one row per milestone of a spec with an `- Epic: E<n>` line, `·` in new cells; existing ticks survive | lead on go, runner on merge |
| `<skill>/scripts/runner.sh start\|list\|stop\|send\|fork\|resume v0.<n>.x` | `start`: reuses the live runner of the release, resumes a dead one, or opens the next `<release> runner<n>` (numbers never reused; `--new` opens another beside the live one; window name is also the `claude -n` name) in the current tmux session running the runner (fable, bypass, fixed `--session-id`, `templates/runner-settings.json`, brief), records it in `~/.claude/expedition-runners.json`, resumes a dead one with `--resume`, prints the command outside tmux; `list`: entries with busy or idle; `stop`: closes the window, marks the entry stopped; `send <release> "<line>"`: types `ultracode <line>` into the runner window and submits it (the RUN line `RUN E<n> <release folder> epic <epic file> from <lead>`); `fork <release> E<n> "<D ids>" --from <lead>`: opens window `<release> specs E<n>` running a forked session of the lead (`--resume $CLAUDE_CODE_SESSION_ID --fork-session`, model fable unless `--model`) that writes the epic's specs and replies `SPECS E<n> <spec numbers>`, with its own `--session-id` in the registry; a fork whose window died is resumed by the same `fork` call, never forked again; `stop "<release> specs E<n>"` closes it; `resume <release or window name>`: types `resume` into a live window (the runner with the ultracode prefix), starts a dead runner, prints the `claude --resume` line for a dead fork | once per release, to revive a runner, and on every go |
| `<skill>/scripts/runner.sh watch start\|stop\|status`, `<skill>/scripts/nudge-watch.sh` | `start`, `send` and `fork` run inside tmux record the calling window as registry key `lead` (`{"tmux": "<session>:<window id>", "session": $CLAUDE_CODE_SESSION_ID, "name": --from or the line's "from <name>"}`); `start` also starts the watcher (pid `~/.claude/expedition-runners/nudge-watch.pid`), `stop` stops it once no runner or fork window is live. The watcher polls the You Should Know store every 5 s and types `NUDGE <source>: <text>` into the lead window for each note shown to a runner, a fork or an unknown session, never one shown to the lead; state `nudge-watch.state` (no replay on restart), log `nudge-watch.log`; exits when `lead` is missing or its window is gone. Env overrides for tests: `NUDGE_STORE`, `NUDGE_STATE`, `NUDGE_LOG`, `NUDGE_REGISTRY`, `NUDGE_INTERVAL` | automatic with `start`; `watch` for manual control |
| `python3 -I <skill>/scripts/new_fix.py v0.<n>.x <slug> "F3, F4"` | creates `run/trackers/fix-<slug>-tracker.md` citing the findings, adds the grid row in the running sprint column | a mid-run fix |
| `python3 -I <skill>/scripts/new_item.py v0.<n>.x D\|F\|A "<title>" [--source A<n>] [--bullet "<text>"]` | under a lock on `.ids.lock` in the release folder: takes the highest id of that kind across the release (A: every ATTENTION file), appends the heading (D and F under the last `## Round` heading, A in today's ATTENTION file, created if missing), the `- Source:` and first bullet if given, commits that file, prints the id alone | every new D, F or A item, by either session |
| `python3 -I <skill>/scripts/find_rules.py [repo]` | read-only: prints project planning-rules paths, one per line, nothing if none | |
| `python3 -I <skill>/scripts/status.py v0.<n>.x` | read-only: missing files, a state table per decision and finding, milestones without tracker, `Status:` line or checks, possible open questions, untriaged ATTENTION items, a `<release>-plan.md` `## ` section other than Goals and Specs, an Specs Scope cell over 120 characters, `status/ownership.md` missing or older than a spec, `status/sprints.md` missing, without a `| Milestone` table, with rows that differ from `status/ownership.md` (fix trackers are `status/ownership.md` rows, so a fix row is never a gap) or with a cell other than `[x]`, `[ ]`, `·`, `[!]`; the `## Critical paths` section and one path line per tagged epic; the release's `process.md` (missing, placeholders left, undefined `(P<n>)` citations), an epic summary (deciding, in E<n>, running, done per D item), the decisions still editable in place, a supersede marked on one side only, an unbuilt spec citing a superseded decision, epic files missing or with notes without ack, the next epic file missing while an epic runs, inferred stage. First line names the planning rules in use | any time |

`<skill>` is this skill's directory.

`status.py` checks only the spec files linked from the `<release>-plan.md` Deliverables table. Other `NN-*.md` files are listed as `supporting:` and not checked. Fix-milestone trackers cite findings on their first line and count as citing. Decision states: `unplanned` (no spec or tracker cites it), `planned`, `running`, `done` (every citing tracker merged or done), `deferred` (a `Deferred to` bullet), `superseded`, `unknown` (a citing tracker has no `Status:` line). Stage inference reports discuss and run together: discuss when there are no decisions, a deciding item or an untriaged ATTENTION item; run when an epic is tagged and not done.

## Template

Precedence, highest first:

1. `--template PATH` on `new_spec.py`.
2. Project planning rules, found by `find_rules.py`: files named like `*plan*guide*.md` or `planning*.md`, and `CLAUDE.md` or `AGENTS.md` lines that mention plan files. `new_spec.py` writes a contract stub and prints each path. The agent then writes the spec by hand in the project's template. The project rules override the bundled guidelines completely: structure, headings, rules, template.
3. Bundled default, only when no project rules are found: [planning-guidelines.md](planning-guidelines.md), template [../templates/spec.md](../templates/spec.md).

The contract applies in all three: citations, the `### Milestone: <name>` blocks, checks per task, no open questions. A project template that lacks one gets it added in that project's style.

## Conventions

- Citations: `(D7)` for a decision, `(F3)` for a finding, `(A2)` for an ATTENTION item, `(P2)` for a process rule, `(v0.4.x D9)` for a decision of another release. `status.py` also reads the older `(decision N)` form.
- `<release>-plan.md` lists `#`, `Spec`, `Scope` only. No duration or size column.
- No questions in plan files. They stay in chat until answered.
- No em dashes in any release file.
