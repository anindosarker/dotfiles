# Release files

## Layout

```
.ai/plans/v0.<n>.x/<owner>/
├── <release>-plan.md       ← authored: ## Goals, ## Deliverables
├── decisions.md            ← accepted decisions, D<n> items under round headings, each with its epic tag line
├── queue.md                ← every item raised in the release, a kanban board: Q<n> cards in five lanes (Open, Decided, Later, Dropped, Autofix)
├── process.md              ← this project's facts for the release, about ten P<n> rules, two to five explicit bullets each (branches, milestone branch and worktree, merge, release, checks on the shared machine, agent sandbox, public surface, commits, shared files, plans); copied from the previous release by new_cycle.py, audited and rewritten rule by rule with the owner before the run (SKILL.md Process notes)
├── plan/specs/NN-<slug>.md ← authored: one spec; follow-up specs NN.M-<slug>.md; section 2.1 holds one ### Milestone: <name> block per milestone
├── plan/epics/E<n>.md     ← one per epic, started by new_epic_file.py: Decisions, Specs and Starts lines, the Ownership table, Notes only when the specs cannot hold something, acked by the runner
├── run/trackers/NN-<slug>-tracker.md ← one per milestone: status, task lines, check lines, staged attention items;
├── run/handoffs/          ← write-handoff output
├── status/sprints.md       ← generated, like everything under status/ (never edited by hand); sprints.py, by go.py and the runner on merge: the grid, one row per milestone, one column per sprint; ticked by the runner
├── status/index.html       ← the swimlane page, copied from templates/swimlanes.html by new_cycle.py, refreshed by swimlanes.py when the template is newer; a render, git-ignored, never committed
├── status/data/sprints.data.js ← regenerated by swimlanes.py (and data/sprints.json): the page's data; git-ignored, never committed
├── status/data/go.log      ← go.py: one line per runner step done (the writer window closed, the RUN line sent) per epic, so a rerun skips it; git-ignored
└── reference/              ← optional supporting material, by hand
```

Older releases (v0.8.x and earlier, and v0.9.x until migrated) keep the flat layout. The scripts do not read them: a folder without `plan/` is refused with one line naming `migrate_layout.py`, which moves it once. A folder still on the old queue files is refused with one line naming `migrate_queue.py`. A folder that still has `status/ownership.md` is refused with one line naming `migrate_epics.py`.

Formats of each file: [formats.md](formats.md).

## <release>-plan.md sections

Exactly two, in order: `## Goals`, `## Deliverables`. No other `## ` section. Process rules are cited `(P<n>)`, never repeated.

Deliverables table: columns `#`, `Spec` (linked to the spec file), `Scope`. Scope is one outcome sentence under 120 characters: no file lists, no mechanics; the spec file holds them.

Milestones live in the spec files, not in `<release>-plan.md`: each spec's section 2.1 holds one `### Milestone: <name>` block per milestone with the lines `- Files owned: a, b`, `- Depends on: <milestone names or spec numbers, or none>`, `- Review: none | fable`, then `- Task 1: ... Checks: ...` lines. Branch and worktree are assigned at launch and recorded in the milestone's tracker, never in the spec.

Checks live in each task's `Checks:` and the release's `process.md`; Acceptance in each spec's `Acceptance:` line (programmatic or judged); the release in the release spec; sandbox rules in `process.md`.

`<release>-plan.md` is not frozen: specs add rows, each go fills their Epic cells.

## Ownership

`ownership.py` computes the ownership facts from those blocks, in memory; no file holds them, and `sprints.py`, `swimlanes.py`, `status.py`, `new_fix.py` and `go.py` call the same code. An edge from A to B exists when B lists A under `Depends on` or when A and B share a file (lower spec number first). A milestone's column is the longest chain ending at it plus one, across every epic, and never before its epic's start sprint: the `Starts: S<n>` line of `plan/epics/E<n>.md`, written on go by `new_spec.py --epic` as the current sprint. The start sprint carries along the edges. An epic file without a `Starts:` value means no floor. A milestone added after go carries its own `- Starts: S<n>` line (`new_fix.py` writes the current sprint), so it never lands in a finished column. A milestone whose grid row is running (`[ ]`) or finished (`[x]`, `[!]`) keeps that column, and a finished one never collides on a shared file. The current sprint is the first column of `status/sprints.md` holding a `[ ]` or `·` cell of an epic row; when there is none, the column after the last column holding an epic row (S1 on an empty grid). For an epic's own start its own rows are ignored. An epic's critical path is the longest chain over that epic's milestones and the edges between them, ties by lower spec number; it is computed where it is shown (the `ownership.py` printout, `status.py`, the swimlane data), never stored. Each epic file's Ownership table shows the epic's share of these facts: the files per decision, the spec and milestones that own them and their sprint ([formats.md](formats.md), Epic file). A file shared by two milestones of the same column, or a dependency cycle, is a script error naming the file and the two milestones, fixed in the spec.

Every file the release changes has exactly one milestone owner while it runs. Two milestones that share a file sit in different columns, or the two merge. Shared files no milestone owns (`<release>-plan.md` appends, changelog blocks, generated registry and docs copies) follow the release's `process.md`. What two or more milestones need (dependency adds, lockfile, lint or CI config, shared helpers, baseline captures) lands as the first sprint's shared milestone.

## status/sprints.md

In `status/`: a title, an `Updated: <date time>` line, one table `Milestone`, `S1` .. `Sn`. Grid only: one row per milestone of a spec with an Epic line, row text `E1 01 Filtering` ([formats.md](formats.md)). A cell is `[x]` merged, `[ ]` running, `·` not started, `[!]` blocked (the reason stays in the milestone's tracker under `## Attention`). No legend, no prose, nothing under the table.

`sprints.py` writes it on go (`go.py`, the epic's rows with `·`) and on merge (the runner); the runner ticks it at every boundary. A regeneration keeps every finished cell (`[x]`, `[!]`) where it is; a running row (`[ ]`) keeps its column (ownership.py pins it) and a not-started row (`·`) is placed again. Then the Sprint column of every unfinished epic's table that has a `Starts:` value follows the grid; nothing else in those files changes, and finished epics' files are left alone. `status.py` flags a `status/sprints.md` whose rows differ from the milestones.

Releases before this rule had free-standing fix milestones: a `run/trackers/fix-<slug>-tracker.md` and a `fix <name>` grid row, with no spec and no epic. The scripts refuse such a folder until `migrate_fixes.py` has moved each one into a follow-up spec of an epic.

## Scripts

Run as `python3 -I <script> <release>` from the repo, a folder inside it, or the folder one level above it: each script takes the git top level of the cwd when it holds `.ai/plans/<release>/`, else the one direct child folder that does (`new_cycle.py`: `.ai/plans/`). Several matches stop with a list; `--root PATH` picks one. They never overwrite an authored file.

`<skill>` is this skill's directory.

`status.py` checks only the spec files linked from the `<release>-plan.md` Deliverables table. Other `NN-*.md` files are listed as `supporting:` and not checked. A tracker no milestone owns counts as citing the queue cards on its first line. Decision states: `unplanned` (no spec or tracker cites it), `planned`, `running`, `done` (every citing tracker merged or done), `deferred` (a `Deferred to` bullet), `superseded`, `unknown` (a citing tracker has no `Status:` line). Stage inference reports discuss and run together: discuss when there are no decisions, a deciding item or a card in Open; run when an epic is tagged and not done.

## Template

Precedence, highest first:

1. `--template PATH` on `new_spec.py`.
2. Project planning rules, found by `find_rules.py`: files named like `*plan*guide*.md` or `planning*.md`, and `CLAUDE.md` or `AGENTS.md` lines that mention plan files. `new_spec.py` writes a contract stub and prints each path. The agent then writes the spec by hand in the project's template. The project rules override the bundled guidelines completely: structure, headings, rules, template.
3. Bundled default, only when no project rules are found: [planning-guidelines.md](planning-guidelines.md), template [../templates/spec.md](../templates/spec.md).

The contract applies in all three: citations, the `### Milestone: <name>` blocks, checks per task, no open questions. A project template that lacks one gets it added in that project's style.

## Conventions

- Citations: `(D7)` for a decision, `(Q3)` for a queue card, `(P2)` for a process rule, `(v0.4.x D9)` for a decision of another release. `status.py` also reads the older `(decision N)` form.
- `<release>-plan.md` lists `#`, `Spec`, `Scope` only. No duration or size column.
- No questions in plan files. They stay in chat until answered.
- No em dashes in any release file.
